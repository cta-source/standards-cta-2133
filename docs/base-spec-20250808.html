Abstract

This document provides a standard binary (JSON) data model for test reports created for the U.S. Cyber Trust Mark program ("USCTM program") or other cybersecurity assessment program. The data model is applicable to the requirements and tests defined USCTM program scheme, and to ISO/IEC 17025 laboratory required data handling and extends to requirements not currently specified or specified in other programs.

This standard was developed by the Consumer Technology Association’s R14 Cybersecurity and Privacy Management Committee. This is an approved and published CTA standard document. All CTA standards are available at CTA.tech/Standards.

1. Introduction

With the release of the FCC’s U.S. Cyber Trust Mark (USCTM), IoT product manufacturers and testing labs will benefit from a standardized format to deliver and interpret USCTM certification results. This document describes that format, hereby referred to as the Format or the Cyber Trust Mark Data Format.

While the USCTM is not publicly released yet, there are various standards that can be used to approximate topics the USCTM will cover. Those standards include ETSI EN 303 645, ANSI/CTA-2088-A, and NISTIR 8425.

2. Scope

This document covers IoT Devices as defined by NISTIR 8425, with the modification proposed by the FCC in their NPRM FCC 23-65. That is, an IoT device consists of at least one transducer, sensor, or actuator, and at least one network interface. This Format does not detail requirements for testing IoT Products, which include at least one Device and additional components such as a cloud backend, mobile app, or gateway device.

5. Definitions, Symbols and Abbreviations

5.1 Definitions

Assessment: The combination of all of the individual Tests required to validate compliance of a product with a Scheme. In order for a product to qualify for certification, it must have a passing result for every individual Test (or, if applicable, a granted Waiver request) enumerated in the Assessment.

Scheme: The scheme is a set of rules and procedures that describes the objects of conformity assessment, identifies the specified requirements, and provides the methodology for performing conformity assessment.

Test: The mechanism by which an individual requirement of a Scheme is validated. Typically, a Test will yield a binary pass/fail result. For example, a Test for encryption strength may make a TLS connection to a device, examine the list of ciphersuites supported by the device, and compare that list to the list of ciphersuites specified by the Scheme. If the list of supported ciphersuites contains only those identified as suitable by the Scheme, then the product will pass that particular Test.

6. Requirements

In the following sections the requirements for the Cyber Trust Mark Data Format are listed and defined.

6.1 Format Structure

The test report shall be comprised of a .json file described below, with supporting files in subdirectories. Note that some of the evidence may be highly compressible, so the use of zip or other standard compression is recommended.

For example:

 ├── index.json 
 └── Tests/
      ├── test_case_number/
 │        ├── evidence.mpg
 │ 
 └── test_case_number/
      ├── result_evidence.jpg
      └── result_log.txt

6.2 JSON Schema

The report data shall conform to the JSON Schema attached as Annex A, which is divided into a Header section which is general information about the product, manufacturer, and lab, and an Assessments section which contains evidence compiled over one or more evaluations of the product against certification requirements to support the certification process. 8. A. Notes on State Diagrams, Flowcharts

8.1 A.1 overall_result field

The overall_result field should be either empty, “pass” or “fail”. If the file is produced by anyone other than a CLA, the overall_result field should not be present. 

When the file is produced by a CLA, it should be signed with CLA credentials.

The overall_result field should be set to “pass” by a CLA if and only if all tests are either “test_pass” or “waiver_granted”.

8.2 A.2 test_result field

The test_result field should be set by the manufacturer, the lab, or the CLA.

When the manufacturer is seeking a waiver for a test without actually running the test, the manufacturer sets the test_result for that test to “Request_Waiver”, and supplies evidence to make its case. The evidence for a waiver could include a Risk Assessment which explains the rationale justifying the waiver, such as the lack of PII or security-critical data in cleartext communication. The ‘runs’ array should contain an appropriate date-time for this request (also see ‘evidence’ in schema).

When the lab runs test(s), the results of those tests are entered into the test_result field. A failing test yields “test_fail”, a passing test yields “test_pass”. Other states are possible – e.g., “error” or “warn”; evaluation of the meaning and next steps for these states require human intervention. In any case, documentation of the running of the test and the results are included in the test results file (see ‘runs’ and ‘evidence’ in schema).

When the manufacturer is seeking a waiver for a test with “test_fail”, or any other state – e.g., “error” or “warn” – the test_result field is set to “request_waiver” and the manufacturer supplies evidence to make its case (see ‘evidence’ in schema).

Note that individual test results and evidence files should be signed. If these elements were not secured, it would be possible for a manufacturer to substitute passing results and falsified evidence prior to submission to the CLA. While no system is perfect, the signing of test results improves the overall integrity of the process. Note that multiple parties (manufacturer, CyberLAB, CLA) may all have reasons for contributing and signing elements of the ultimate results file.

When the file is produced by a CLA, the file header including overall assessment result should be signed with CLA credentials if the overall result is a pass.

When the file is produced by the lab for consumption by the CLA, the data elements entered by the CyberLAB should be signed with lab credentials.

When the file is produced by the manufacturer for consumption by the lab, the data elements entered by the manufacturer should be signed with manufacturer credentials.

Anticipated Flow

For a test, if the manufacturer seeks a waiver without running the test, the manufacturer provides documentation/evidence, and the lab sets the test result to “seeking_waiver”.

In other cases, the test is run. Evidence produced by the test run is added to evidence. For passing tests, the test_result is set to ‘pass’. For failing results, the manufacturer may stop the process and return to development, or it may seek a waiver by providing evidence/argument for the waiver and the lab sets the test_result to “seeking_waiver” and includes evidence (including the manufacturer’s arguments) in the generated file. The manufacturer may also request a re-test, in which case the process resumes from a new test run.

For the case where the result of a test is a state other than pass or fail, a human should review the result and evidence of that state shall be included in the evidence.

The file format supports recording of information about why specific Tests are not repeated in a particular test run. A CyberLAB might choose to record this information for subsequent reference or documentation that particular Test results are not expected to be different as a result of a configuration change required for other Tests to pass.
